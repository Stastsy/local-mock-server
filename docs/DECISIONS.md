# Decision log

Short records of decisions that shape the project, with the reason and the alternative that was
rejected. Newest last. Owned by the orchestrator.

---

## D-001 — OpenAPI 3.0.x only in the MVP

**Decision.** The server accepts OpenAPI 3.0.x. Documents declaring 3.1.x or Swagger 2.0 are
rejected at load time with `UNSUPPORTED_SPEC_VERSION` and a message naming the detected version.

**Why.** 3.1 is built on JSON Schema 2020-12: a different AJV draft, `nullable` replaced by type
arrays, different `exclusiveMinimum` semantics. Supporting it means two validation branches and
roughly double the QA surface. Swagger 2.0 is a different document model altogether
(`definitions`, body parameters, `produces`).

**Rejected.** 3.0 + 3.1; 3.0 + 3.1 + Swagger 2.0. Both were judged to put the MVP at risk for a
learning project. Extending to 3.1 is a clean follow-up iteration once the MVP is accepted.

---

## D-002 — Response selection is controlled by the `Prefer` header

**Decision.** Clients steer the mock with `Prefer: code=404` and `Prefer: example=notFound`.
Query parameters are never used as a control channel.

**Why.** It is the established convention for mock servers (Stoplight Prism uses it), it keeps URLs
clean, and — decisively — it cannot collide with query parameters declared in the specification.

**Rejected.** `__code` / `__example` query parameters (collision risk with real parameters);
supporting both (doubles the acceptance matrix for combinations and precedence).

---

## D-003 — The Developer may read and run the acceptance suite but never edit it

**Decision.** `qa/**` is read-only for the Developer agent. Enforced by the orchestrator via
`git diff --name-only <QA_SHA>..HEAD -- qa/` after every iteration; a non-empty result fails the
iteration and the directory is restored with `git checkout <QA_SHA> -- qa/`.

**Why.** Classic ATDD. Blind development against failure logs alone was considered and rejected as
impractical — it multiplies iterations without adding independence, because the tests are already
written and frozen. Full write access was rejected because it destroys the independence of testing,
which is the main thing this project sets out to demonstrate.

**Note on enforcement.** Claude Code has no per-subagent filesystem permissions: the `tools` field
restricts *which tools* an agent may use, not *which paths* it may touch. Instructions in
`CLAUDE.md` and in the agent definition are therefore advisory; the git check is the actual gate.
A `PreToolUse` hook denying `Edit`/`Write` on `qa/**` is available as a hard backstop, but it
applies to the whole session and cannot distinguish subagents — so it may only be switched on once
the QA stage is complete.

**Confirmed in practice, the hard way.** Claude Code reads subagent definitions at session start.
The agent files in `.claude/agents/` were created *during* the session that then used them, so they
were not registered: the Business Analyst and QA Engineer ran as general-purpose agents following
their role file as an instruction, with the `tools` restriction that file declares having no effect
at all. The Business Analyst later disclosed, unprompted, that it had run one read-only shell
command — something its role forbids and its configuration was supposed to make impossible. Nobody
would otherwise have noticed, since subagent transcripts are not read back.

Nothing was damaged, but the lesson stands and is the reason this decision reads as it does: the
boundary that actually held was the git check, because it is mechanical and runs outside the agent.
A restriction that exists only as text in a prompt is a request, not a control. Agent definitions
created in a session take effect from the *next* session onward.

## D-004 — Response data is generated by json-schema-faker with a fixed seed

**Decision.** `json-schema-faker` produces data where the specification provides no example.
The seed comes from `--seed` (default 1) so that equal seeds yield equal responses.

**Why.** It understands formats, enums, bounds and nesting out of the box, which is most of the
work. A fixed seed removes the flakiness that generated data would otherwise cause in tests.

**Rejected.** A hand-written generator (roughly a module plus its own unit tests, for a benefit the
MVP does not need yet); `@faker-js/faker` with a hand-written schema walk (similar cost).

**Measured behaviour (`json-schema-faker` 0.6.3).** The installed version exposes a functional API
(`generateSync(schema, { seed })`, `createGeneratorSync`) rather than the global singleton of older
releases. Verified on this project: a seeded `generateSync` call is reproducible, including across
separate processes, and covers `pattern` and `format: date-time`; generator instances share no
state; a single instance created by `createGeneratorSync` advances its PRNG between calls. The seed
is therefore applied per generation call and never by reusing a long-lived instance — see
`docs/ARCHITECTURE.md` §7.

**Containment.** The library sits behind the `ResponseGenerator` interface and — because acceptance
tests assert schema conformance rather than values (D-005) — replacing it later would not touch a
single acceptance test.

## D-005 — Acceptance tests use real HTTP and assert schema conformance

**Decision.** The acceptance suite calls `createServer({ port: 0 })` / `start()` and then uses
`fetch`. It never uses `fastify.inject()` and imports nothing from `src/` beyond `createServer`.
Response bodies are validated against the schema from the specification; exact values are asserted
only where the specification prescribes them.

**Why.** These two rules are what make QA's suite independent of the Developer's choices: the HTTP
framework and the data generator can both be replaced without touching a test. The cost is roughly
200 ms per suite for real socket binding, which is negligible here.

**Rejected.** `app.inject()` for speed — it would make the suite depend on Fastify being the
framework, i.e. on an implementation detail the Developer owns.

## D-006 — A document declaring both `example` and `examples` is accepted

**Decision.** The OpenAPI 3.0 meta-schema is enforced at load time with one exception:
`ExampleXORExamples` on the Media Type Object. A document that declares both keywords loads
successfully, and REQ-033's precedence decides which value is served — `example` wins.

**Why.** The two requirements were in genuine conflict: REQ-033 specifies what to serve when both
are present, while REQ-004 requires an invalid document to be rejected, and `SwaggerParser.validate`
does reject exactly that document. Verified directly rather than taken on report. Declaring both is
a common authoring mistake, and other mock tools tolerate it; rejecting the document would trade a
working mock for meta-schema purity.

**Rejected.** Enforcing the meta-schema strictly and withdrawing REQ-033's third precedence
criterion. It is the more conformant reading, but it makes the tool refuse specifications people
actually have, and it would have churned three agents' artifacts to get there.

**Implementation note.** The server validates a sanitised copy of the document and serves the
original, which keeps both keywords. That is an implementation detail; the requirements specify only
the observable behaviour.

---

## D-007 — Generated values are re-validated before they are served

**Decision.** Every value produced by the data generator is validated against the schema it was
generated from. A value that does not conform is not served: the request fails with
`GENERATION_FAILED`.

**Why.** `json-schema-faker` does not enforce contradictory constraints — measured on this project,
`generateSync({ type: 'string', minLength: 5, maxLength: 2 }, { seed: 1 })` returns `"aG8"`, which
satisfies neither bound. Without the re-validation step REQ-040 would not hold, and worse, it would
not visibly fail: the server would answer `200` with a body that does not match its own
specification, which is precisely the failure a mock server exists to prevent.

**Consequence.** This step is load-bearing, not defensive polish. Removing it as an optimisation
would silently regress REQ-040 from an error into a passing response with a non-conforming body.

**Known limitation.** The re-validation uses the same AJV instance and the same OAS-to-JSON-Schema
converter that the acceptance suite uses for its own assertions (`docs/TEST-PLAN.md` §7.1). A bug in
the converter would therefore be invisible to both sides. Accepted: an independent second validator
costs more than the risk it removes.
