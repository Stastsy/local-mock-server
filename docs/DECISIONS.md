# Decision log

Short records of decisions that shape the project, with the reason and the alternative that was
rejected. Newest last. Owned by the orchestrator.

---

## D-001 — OpenAPI 3.0.x only in the MVP

**Decision.** The server accepts OpenAPI 3.0.x. Documents declaring 3.1.x or Swagger 2.0 are
rejected at load time with `UNSUPPORTED_SPEC_VERSION` and a message naming the detected version.

**Why.** 3.1 is built on JSON Schema 2020-12: a different AJV draft, `nullable` replaced by type
arrays, different `exclusiveMinimum` semantics. Supporting it means two validation branches and
roughly double the QA surface. Swagger 2.0 is a different document model altogether
(`definitions`, body parameters, `produces`).

**Rejected.** 3.0 + 3.1; 3.0 + 3.1 + Swagger 2.0. Both were judged to put the MVP at risk for a
learning project. Extending to 3.1 is a clean follow-up iteration once the MVP is accepted.

---

## D-002 — Response selection is controlled by the `Prefer` header

**Decision.** Clients steer the mock with `Prefer: code=404` and `Prefer: example=notFound`.
Query parameters are never used as a control channel.

**Why.** It is the established convention for mock servers (Stoplight Prism uses it), it keeps URLs
clean, and — decisively — it cannot collide with query parameters declared in the specification.

**Rejected.** `__code` / `__example` query parameters (collision risk with real parameters);
supporting both (doubles the acceptance matrix for combinations and precedence).

---

## D-003 — The Developer may read and run the acceptance suite but never edit it

**Decision.** `qa/**` is read-only for the Developer agent. Enforced by the orchestrator via
`git diff --name-only <QA_SHA>..HEAD -- qa/` after every iteration; a non-empty result fails the
iteration and the directory is restored with `git checkout <QA_SHA> -- qa/`.

**Why.** Classic ATDD. Blind development against failure logs alone was considered and rejected as
impractical — it multiplies iterations without adding independence, because the tests are already
written and frozen. Full write access was rejected because it destroys the independence of testing,
which is the main thing this project sets out to demonstrate.

**Note on enforcement.** Claude Code has no per-subagent filesystem permissions: the `tools` field
restricts *which tools* an agent may use, not *which paths* it may touch. Instructions in
`CLAUDE.md` and in the agent definition are therefore advisory; the git check is the actual gate.
A `PreToolUse` hook denying `Edit`/`Write` on `qa/**` is available as a hard backstop, but it
applies to the whole session and cannot distinguish subagents — so it may only be switched on once
the QA stage is complete.

## D-004 — Response data is generated by json-schema-faker with a fixed seed

**Decision.** `json-schema-faker` produces data where the specification provides no example.
The seed comes from `--seed` (default 1) so that equal seeds yield equal responses.

**Why.** It understands formats, enums, bounds and nesting out of the box, which is most of the
work. A fixed seed removes the flakiness that generated data would otherwise cause in tests.

**Rejected.** A hand-written generator (roughly a module plus its own unit tests, for a benefit the
MVP does not need yet); `@faker-js/faker` with a hand-written schema walk (similar cost).

**Risk and containment.** `json-schema-faker` is not actively developed. It sits behind the
`ResponseGenerator` interface, and — because acceptance tests assert schema conformance rather than
values — replacing it later would not touch a single acceptance test.

---

## D-005 — Acceptance tests use real HTTP and assert schema conformance

**Decision.** The acceptance suite calls `createServer({ port: 0 })` / `start()` and then uses
`fetch`. It never uses `fastify.inject()` and imports nothing from `src/` beyond `createServer`.
Response bodies are validated against the schema from the specification; exact values are asserted
only where the specification prescribes them.

**Why.** These two rules are what make QA's suite independent of the Developer's choices: the HTTP
framework and the data generator can both be replaced without touching a test. The cost is roughly
200 ms per suite for real socket binding, which is negligible here.

**Rejected.** `app.inject()` for speed — it would make the suite depend on Fastify being the
framework, i.e. on an implementation detail the Developer owns.
